## 1. Introduction

**AntlrAndDragons** is a statically typed imperative programming language developed with ANTLR4 as a DSL (*Domain Specific Language*), inspired by the mechanics of fantasy role-playing games, in particular Dungeons & Dragons (DnD).

## 2. Design Choices

The language was designed as a DSL (Domain Specific Language) with the goal of providing expressive constructs that are thematically consistent with the RPG domain, while retaining features typical of modern programming languages:

- **Static typing**, with domain types dedicated to role-playing games (`HP`, `Level`, `Damage`, `QuestName`, `Die`);
- **Classes and objects**, via the `creature` construct;
- **Functions**, via the `spell` construct;
- **Conditional control flow**;
- **Type conversions**, both implicit for compatible types within the hierarchy and explicit via casting;
- **Syntactic sugar**: compound assignments (`+=`, `-=`, `*=`, `/=`), unary increment and decrement (`++`, `--`) with pre and post precedence, ternary operator (`_ ? _ : _`), and expression interpolation inside strings (`i"...${expr}..."`);
- **Structured management of program sections**, with distinct sections for creatures, globals, functions, and the main block.
- **User input**, via `declare(Type,prompt)`, with runtime type validation.

The interpreter was implemented with ANTLR4 in IntelliJ IDEA, leveraging the parser and visitor automatically generated from the grammar.

### 2.1 Application context

The language is designed for those who want to program role-playing game experiences in a natural and expressive way.

The main use cases include modeling creatures with stats and behaviors, defining spells and abilities as callable functions, simulating combat through dice rolls and conditional logic, and managing quests with narrative events and branching flows.

To reinforce this thematic consistency, the language's keywords are inspired by the fantasy world: `creature` instead of `class`, `spell` instead of `function`, `quest` for the main block, `summon` for object creation, `roll` for dice rolling, `narrate` for printing to screen, `flee` for exiting the program. This makes the code immediately readable within its application context, bringing the syntax closer to the natural language of the domain.

### 2.2 RPG mechanics

The language directly integrates some mechanics typical of role-playing games, turning them into first-class constructs:

- **Dice rolling** via the `roll` construct, which supports the standard `NdX` notation (e.g. `roll 2d6` rolls two six-sided dice and returns the sum);
- **`Die` type**, a subtype of `String`, to represent and manipulate dice notations as language values;
- **Object creation** via `summon CreatureName`, equivalent to a typed `new` in the domain;
- **Interpolated strings** with the `i"...${expr}..."` syntax, which allows evaluated expressions to be embedded directly in text, useful for dynamic narrative messages.

### 2.3 Control constructs

The language supports a complete set of constructs for controlling flow:

- `if / else if / else` for conditional selection;
- `until (cond) { }` as an alternative to `while`, which continues as long as the condition is false and stops once it becomes true;
- `for x from e1 to e2 { } else { }`, a loop with an explicit iteration variable and an optional `else` block executed only if the loop completes without a `break`;
- `switch (e) { case ... }` with fall-through support and an optional `default` clause;
- ternary operator `cond ? a : b` for inline selection;
- `break` for early exit from loops and switches;
- `return` to return a value from a function;
- `flee` for immediate program termination.

## 4. Syntax

### 4.1 Program structure

A program consists of three main sections:

```text
program : creaturesSection? globalSection? spellbookSection? questBlock EOF ;
```
The `globalSection` is the optional section dedicated to declaring global variables.

The `creaturesSection` and `spellbookSection` sections are, respectively, the optional declarative sections for classes and functions.

The `quest` section represents the program's entry point; it contains the program body enclosed in a `{ ... }` block.

---

### 4.2 Creatures and classes

```
creatureDecl : CREATURE ID '{' creatureMember* '}' ;

creatureMember : type ID ';'                        # ClassField
               | type ID '(' paramList? ')' block   # ClassMethodReturn
               | VOID ID '(' paramList? ')' block   # ClassMethodVoid
               ;
```

A class can contain:

* fields;
* methods with a return value;
* void methods;

---

### 4.3 Functions

Functions are defined in the `spellbook` section.

```
spellDecl : SPELL type ID '(' paramList? ')' block   # FuncDeclReturn
          | SPELL VOID ID '(' paramList? ')' block   # FuncDeclVoid
          ;
```

They can:

* return values;
* be `void`;
* receive typed parameters.


---

### 4.4 Data types

| Type        | Description                                       |
| ----------- | ------------------------------------------------- |
| `Int`       | Signed integer                                  |
| `Float`     | Real number                                      |
| `Bool`      | Boolean value                                   |
| `String`    | Text string                                      |
| `HP`        | Hit points, semantic subtype of `Int`          |
| `Damage`    | Damage, semantic subtype of `Int`               |
| `Level`     | Character level, semantic subtype of `Int` |
| `QuestName` | Quest name, derived from `String`               |
| `Die`       | Type dedicated to RPG dice, subtype of `String`  |
| `Any`       | Universal supertype |

The types HP, Damage, and Level are semantic subtypes of Int: widening `(HP → Int, Int → Float)` happens implicitly,
while narrowing `(Int → HP)` requires an explicit cast. Similarly, QuestName and Die are subtypes of String:
the assignment `QuestName → String` is implicit, while `String → QuestName` requires an explicit cast.

### 4.5 Syntactic Sugar

Compound operators, the ternary operator, and interpolated strings are supported:

* `+=`
* `-=`
* `*=`
* `/=`
* `%=`
* `String status = (hp gt 0) ? "Alive" : "Dead";`
* `narrate i"The result of x * y is ${x * y}";`

### Compound assignment

```text
Mage.hp=20;
atk = goblin.cast ClawAttack(); //(type Damage)

Mage.hp -= (HP) atk; 
```

### Increment and decrement

The language supports pre- and post-unary increment/decrement:

```text
++x;
x++;
--x;
x--;
```

---
### 4.6 Expressions

Our hierarchy is consistent with traditional languages.

| Precedence (highest to lowest) | Operators                                                      |
|--------------------------------------------|----------------------------------------------------------------|
| 1                                          | Primary expressions: literals, identifiers, summon, declare, (expr), function calls|
| 2                                          | `.` (field access and method calls)                      |
| 3                                          | Unary operators: `not`, `-`, cast `(Type)`, `++`, `--`, `roll` |
| 4                                          | `*`, `/`, `%`                                                  |
| 5                                          | `+`, `-`                                                       |
| 6                                          | `lt`, `gt`, `lte`, `gte`                                       |
| 7                                          | `eq`, `neq`                                                    |
| 8                                          | `and`                                                          |
| 9                                          | `or`                                                           |
| 10                                          | `?:` (ternary operator, **right-associative**)            |

Primary expressions (summon, literals, identifiers, declare, (expr)) are non-recursive alternatives and are
always resolved first, regardless of their position in the grammar.


### 4.8 Interpolated strings

Strings prefixed with `i` support expression interpolation via `${...}`:

```
narrate i"HP remaining: ${hp}";
narrate i"Base damage + bonus = ${damage + 5}";
```

---

### 4.9 User input

```
declare(Type, "prompt message")
```

Shows the prompt to the user, waits for keyboard input, and converts it to the specified type. The expected type must be explicitly indicated:

Any is the universal supertype: any value can be implicitly assigned to an Any variable. The reverse
assignment (Any to a concrete type) instead requires an explicit cast. For example:
```
Any x = declare(Any, "Enter a number:"); // OK: type Any
Int x = declare(Any, "Enter a number:"); // NOT OK! 
Int x = (Int) declare(Any, "Enter a number:"); // OK: explicit cast Any -> Int
```

#### Limitations:
* The syntax `declare(Type, "optional prompt")` requires the expected type to be explicitly declared
  within the call. This design choice allows the type checker to statically infer the
  type returned by the expression, making it possible to verify compatibility with the variable to which the
  value is assigned already during static analysis. Without the type, the type checker would be forced to
  return `Any`, weakening the static guarantees of the type system.

## 5. Operational Semantics

Below we show the transition rules of AntlrAndDragons' operational semantics.

The state is a pair $(\overline{\sigma}, c)$ where $\overline{\sigma} = \sigma_1 \cdot \sigma_2 \cdot \ldots \cdot \sigma_n$ is a stack of memories (a memory $\sigma$ is a map from identifiers to values) and $c$ is the command (or expression) to be evaluated.

### 5.1 Until

$$
\text{Until-False} ~ \frac{
(\overline{\sigma},\ e) \rightarrow \texttt{false}
\quad
(\overline{\sigma},\ c) \rightarrow \overline{\sigma}'
\quad
(\overline{\sigma}',\ \texttt{until}\ (e)\ \{c\}) \rightarrow \overline{\sigma}''
}{
(\overline{\sigma},\ \texttt{until}\ (e)\ \{c\}) \rightarrow \overline{\sigma}''
}
$$



$$
\text{Until-True} ~ \frac{
(\overline{\sigma},\ e) \rightarrow \texttt{true}
}{
(\overline{\sigma},\ \texttt{until}\ (e)\ \{c\}) \rightarrow \overline{\sigma}
}
$$



$$
\text{Until-Break} ~ \frac{
(\overline{\sigma},\ e) \rightarrow \texttt{false}
\quad
(\overline{\sigma},\ c) \rightarrow \texttt{break}
}{
(\overline{\sigma},\ \texttt{until}\ (e)\ \{c\}) \rightarrow \overline{\sigma}
}
$$

---

### 5.2 Switch-case-default

We use the notation $\texttt{switch}\ (e)\ \{cs\}$ where $cs$ is the list of clauses, and we write the cases as $\texttt{case}\ v: \overline{s}$ and the default as $\texttt{default}: \overline{s}$.


$$
\text{Switch-case} ~ \frac{
(\overline{\sigma},\ e) \rightarrow v
\quad
(\overline{\sigma},\ e_i) \rightarrow v
\quad
(\overline{\sigma},\ \overline{s}_i) \rightarrow \overline{\sigma}'
}{
(\overline{\sigma},\ \texttt{switch}\ (e)\ \{\ldots,\ \texttt{case}\ e_i: \overline{s}_i,\ \ldots\}) \rightarrow \overline{\sigma}'
}
$$



$$
\text{Switch-Default} ~ \frac{
(\overline{\sigma},\ e) \rightarrow v
\quad
\forall i.\ (\overline{\sigma},\ e_i) \rightarrow v_i \land v_i \neq v
\quad
(\overline{\sigma},\ \overline{s}_d) \rightarrow \overline{\sigma}'
}{
(\overline{\sigma},\ \texttt{switch}\ (e)\ \{\texttt{case}\ e_1: \overline{s}_1,\ \ldots,\ \texttt{case}\ e_n: \overline{s}_n,\ \texttt{default}: \overline{s}_d\}) \rightarrow \overline{\sigma}'
}
$$

$$
\text{Switch-NoMatch} ~ \frac{
(\overline{\sigma},\ e) \rightarrow v
\quad
\forall i.\ (\overline{\sigma},\ e_i) \rightarrow v_i \land v_i \neq v
\quad
}{
(\overline{\sigma},\ \texttt{switch}\ (e)\ \{\texttt{case}\ e_1: \overline{s}_1,\ \ldots,\ \texttt{case}\ e_n: \overline{s}_n\}) \rightarrow \overline{\sigma}
}
$$

---

### 5.3 For-else-break

`for x from e1 to e2 { c } else { c_else }` — iterates `x` from `e1` to `e2`, with an optional `else` block that is executed **only if the loop completes normally** (without `break`).

In For-Break: with dynamic scoping, each block pushes a new frame onto the stack and pops it at the end.

We use the notation $\sigma_x = \{x \mapsto n_1\}$ for the frame containing only `x`, and the stack becomes $\sigma_x \cdot \overline{\sigma}$ upon entering the block, and returns to $\overline{\sigma}$ upon exiting.

$$
\text{For-Step} ~ \frac{
(\overline{\sigma},\ e_1) \rightarrow n_1
\quad
(\overline{\sigma},\ e_2) \rightarrow n_2
\quad
n_1 \leq n_2
\quad
(\{x \mapsto n_1\} \cdot \overline{\sigma},\ c) \rightarrow \overline{\sigma}'
\quad
(\overline{\sigma}',\ \texttt{for}\ x\ \texttt{from}\ (n_1{+}1)\ \texttt{to}\ e_2\ \{c\}) \rightarrow \overline{\sigma}''
}{
(\overline{\sigma},\ \texttt{for}\ x\ \texttt{from}\ e_1\ \texttt{to}\ e_2\ \{c\}) \rightarrow \overline{\sigma}''
}
$$

$$
\text{For-Done} ~ \frac{
(\overline{\sigma},\ e_1) \rightarrow n_1
\quad
(\overline{\sigma},\ e_2) \rightarrow n_2
\quad
n_1 > n_2
}{
(\overline{\sigma},\ \texttt{for}\ x\ \texttt{from}\ e_1\ \texttt{to}\ e_2\ \{c\}) \rightarrow \overline{\sigma}
}
$$



$$
\text{For-Else} ~ \frac{
(\overline{\sigma},\ e_1) \rightarrow n_1
\quad
(\overline{\sigma},\ e_2) \rightarrow n_2
\quad
n_1 > n_2
\quad
(\overline{\sigma},\ c_{else}) \rightarrow \overline{\sigma}'
}{
(\overline{\sigma},\ \texttt{for}\ x\ \texttt{from}\ e_1\ \texttt{to}\ e_2\ \{c\}\ \texttt{else}\ \{c_{else}\}) \rightarrow \overline{\sigma}'
}
$$



$$
\text{For-Break} ~ \frac{
(\overline{\sigma},\ e_1) \rightarrow n_1
\quad
(\overline{\sigma},\ e_2) \rightarrow n_2
\quad
n_1 \leq n_2
\quad
(\{x \mapsto n_1\} \cdot \overline{\sigma},\ c) \rightarrow \texttt{break}
}{
(\overline{\sigma},\ \texttt{for}\ x\ \texttt{from}\ e_1\ \texttt{to}\ e_2\ \{c\}\ \texttt{else}\ \{c_{else}\}) \rightarrow \overline{\sigma}
}
$$

## 6. Implementation

### 6.1 Memory management — `Mem`

The `Mem` class is the core of scope management. It maintains a `Deque<Scope>` where each `Scope` contains:

- `Map<String, ExpType> types` — declared type of each variable
- `Map<String, ExpValue<?>> values` — runtime value (can be `null` if not initialized)

#### Main operations

| Method | Description |
|---|---|
| `pushScope()` | Adds a new frame to the top of the stack |
| `popScope()` | Removes the top frame |
| `declare(id, type)` | Declares a variable without a value |
| `declareInit(id, type, val)` | Declares and initializes a variable |
| `getValue(id)` | Looks up the value by walking up the scope stack |
| `getType(id)` | Looks up the declared type by walking up the stack |
| `setValue(id, val)` | Updates the value by walking up the stack |
| `contains(id)` | True if the variable is declared *and* initialized |
| `isDeclared(id)` | True if the variable is declared (even without a value) |
| `mergeFrom(other)` | Merges values back from a cloned memory |
| `copyOf(other)` | Creates an independent copy (for branching) |

The lookup in `getValue`, `getType`, and `setValue` traverses the stack from top to bottom, implementing dynamic scoping semantics.

---

### 6.2 Dynamic scoping

AntlrAndDragons implements **dynamic scoping**: variable resolution happens on the active scope stack *at runtime*, not on the static lexical structure of the source code.

#### How it works

Memory is managed by the `Mem` class, which maintains a `Deque<Scope>` — a stack of frames. Each frame contains a `name → type` map and a `name → value` map. Looking up a variable traverses the stack from the top (innermost scope) down to the bottom (global scope), returning the first match found.

When entering a `{ ... }` block, `pushScope()` is executed. On exit (even in case of exceptions), `popScope()` is executed, guaranteed by a `finally` block.

#### Example

```
world:
    Int x = 10;

spellbook:
    spell Int readX() {
        return x;
    }

quest:
{
    narrate cast readX();    // prints 10 (sees x = 10 from the global scope)
    {
        Int x = 11;
        narrate cast readX();    // prints 11 (x = 11 is now on top of the stack)
    }
    narrate cast readX();    // prints 10 (the inner block has ended, x = 11 no longer exists)
}
```

**Output:** `10`, `11`, `10`

---

### 6.3 Variable shadowing

BagOfGrammar supports the phenomenon of **shadowing**.

Shadowing occurs when a variable declared in an inner scope has the same name as a variable declared in an outer scope. In this case, the inner variable takes precedence and temporarily hides the outer one for the entire duration of the scope in which it is defined.

Example:

```text
Int hp = 100;

{
    Int hp = 50;

    narrate hp;
}

narrate hp;
```

**Output:** `50`, `100`

Shadowing is handled naturally by the stack-based scope structure used by the interpreter. When looking up a variable, the interpreter examines the active scopes starting from the innermost one; the first declaration found is used, and any declarations with the same name in outer scopes are ignored.


---

### 6.4 Pass-by-value parameter passing

Function parameters are passed **by value**: at call time, the argument values are copied into new local variables in the function's scope. Modifications to parameters inside the function do not affect the caller's variables.

**Execution sequence of a call:**

1. The arguments are evaluated in the caller's scope.
2. A new scope is created with `pushScope()`.
3. The formal parameters are declared and initialized with the copied values (`bindParams`).
4. The function body is executed.
5. On `return`, a `ReturnException` is thrown, carrying the return value.
6. The local scope is removed with `popScope()` in the `finally` block.


### Remark — Parameter passing and objects

The language adopts **pass-by-value** uniformly.

For **primitive types** (`Int`, `Float`, `Bool`, `String`, and the domain types) this guarantees complete isolation: the function receives a copy, and local modifications do not propagate to the caller.

For **objects**, the value passed is a *reference* to the heap instance — not the object itself. The function therefore receives a copy of the reference, which points to the same object as the caller's. As a result:

- **reassigning the parameter** (e.g. `param = summon OtherObject()`) has no effect outside the function;
- **modifying fields** (e.g. `param.hp -= 10`) produces a side effect visible to the caller, because both point to the same instance.

This behavior is identical to Java's.

```
creatures:
    creature Goblin { 
        HP hp; 
    }

spellbook:
    spell void heal(Goblin g) {
        g.hp += (HP) 20;           // modification visible to the caller
        g = summon Goblin();    // local reassignment: ignored by the caller
    }

quest:
{
    Goblin enemy = summon Goblin();
    enemy.hp = (HP) 30;
    cast heal(enemy);
    narrate enemy.hp;   // prints 50, not 30
}
```

### 6.5 The type checker (`BagOfGrammarTS`)

Similarly to the interpreter, the type checker extends (`BagOfGrammarBaseVisitor<Type>`), adopting a uniform
return type for all AST nodes: expression visitors return the inferred Type, while statement
visitors return null, conventionally used as a sentinel value to indicate the absence of a type,
analogous to the void type of the C language. It runs **before** the interpreter and statically checks type
correctness, using a `Mem` structure similar to the interpreter's but working with types instead of values.

The main checks include:

- Variable declarations and usage
- Type compatibility in expressions and assignments
- Correctness of `return` statements with respect to the function's return type
- Matching of arguments in function calls
- Existence of classes and methods in object accesses

### Static typing

The language adopts **static typing**: every variable has a type fixed at declaration, verified before execution by the type checker (`BagOfGrammarTS`). Attempts to assign incompatible values are detected statically.

Correct example:

```text
Int x = 10;
```

Incorrect example:

```text
Int x = "hello";
```

The error is detected during semantic checking.


### Type hierarchy

The language implements a semantic type hierarchy.

```
Any
├── Bool
├── String
│   ├── QuestName
│   └── Die
└── Float
    └── Int
        ├── HP
        ├── Damage
        └── Level
```

* The type hierarchy has a root type `Any` from which all the language's types derive.
* `HP`, `Damage`, and `Level` are semantic subtypes of `Int`, and can be used wherever an `Int` is expected.
* `QuestName` and `Die` are semantic subtypes of `String`, and can be used wherever a `String` is expected.

Numeric conversions follow the chains:

$$
\text{HP} \subsetneq \text{Int} \subsetneq \text{Any} \\
$$
$$
\text{Damage} \subsetneq \text{Int} \subsetneq \text{Any} \\
$$
$$
\text{Level} \subsetneq \text{Int} \subsetneq \text{Any} \\
$$

Non-numeric conversions follow the chains:

$$
\text{QuestName} \subsetneq \text{String} \subsetneq \text{Any} \\
$$
$$
\text{Die} \subsetneq \text{String} \subsetneq \text{Any} \\
$$



### Type compatibility

A variable can receive:

* values of the same type;
* values of subtypes (implicit widening: e.g. HP → Int, Int → Float). Narrowing (e.g. Int → HP, Float → Int)
  requires an explicit cast.

Example:

```text
Int x = 10;
Damage d = 5;

x = d;
```

Since `Damage` is semantically compatible with `Int`, the assignment is valid.

Compatibility is centralized in the `isAssignable(Type from, Type to)` method, which encodes all of the language's assignability rules in a single place:

```java
private boolean isAssignable(Type from, Type to) {
    if (from instanceof ErrType || to instanceof ErrType) return true;
    if (to == SimpleType.ANY) return true;
    if (from.equals(to)) return true;

    // Subtyping: HP, Damage, Level subtypes of Int
    if ((from == SimpleType.HP || from == SimpleType.DAMAGE || from == SimpleType.LEVEL)
            && to == SimpleType.INT) return true;

    // Subtyping: QuestName, Die subtypes of String
    if ((from == SimpleType.QUESTNAME || from == SimpleType.DIE)
            && to == SimpleType.STRING) return true;

    // Numeric widening
    if ((from == SimpleType.INT || from == SimpleType.HP ||
            from == SimpleType.DAMAGE || from == SimpleType.LEVEL)
            && to == SimpleType.FLOAT) return true;

    if (from instanceof ObjectType && to instanceof ObjectType)
        return ((ObjectType) from).getName().equals(((ObjectType) to).getName());

    return false;
}
```

### Type Conversion

#### Explicit cast

The language distinguishes two categories of type conversion. Implicit widening happens automatically when a
subtype is assigned to its supertype (e.g. HP → Int, Int → Float, QuestName → String). Explicit narrowing
requires a cast in the form (Type) expression and is mandatory when converting a supertype into a
subtype (e.g. Int → HP, Float → Int, String → QuestName). An incorrect explicit cast (e.g. (Int) "hello") produces
a runtime error.

```text
(Float) x
(Int) y
```

The grammar:

```text
'(' type ')' expr
```

### 6.6 The Interpreter (`BagOfGrammarIntp`)

The interpreter's visitor extends BagOfGrammarBaseVisitor<ExpValue<?>>), adopting a uniform return type
for all AST (Abstract Syntax Tree) nodes: expression visitors return a concrete ExpValue<?>, while statement
visitors return `null`, conventionally used as a sentinel value to indicate the absence of a
result, analogous to the void type of the C language.

### Memory and dynamic scoping

Memory is managed by the `Mem` class, which internally maintains a **stack of frames** (scope stack). Each frame is a map from identifiers to values. The main operations are `pushScope()`, `popScope()`, `declareInit()`, and `setValue()` / `getValue()`.

Scoping is **dynamic**: when entering a block a new frame is pushed, and when leaving it, it is popped — regardless of where the block was defined. This means that a called function sees the variables of the context from which it is invoked, not the one in which it was declared.

```java
@Override
public ExpValue<?> visitBlock(BagOfGrammarParser.BlockContext ctx) {
    mem.pushScope();
    try {
        for (BagOfGrammarParser.StatContext s : ctx.stat())
            visit(s);
    } finally {
        mem.popScope(); // pop guaranteed even in case of exception
    }
    return null;
}
```

The `finally` block guarantees that the frame is always removed even if a `BreakException` or `ReturnException` is thrown during execution.

---

### Control flow signals

The language supports `break`, `return`, and `flee` (exit). Instead of using sentinel values or boolean flags, the interpreter uses Java exceptions as **control flow signals**, an effective pattern in tree-walking interpreters:

```java
private static class ReturnException extends RuntimeException {
    final ExpValue<?> value;
    ReturnException(ExpValue<?> value) { ... }
}

private static class BreakException extends RuntimeException {
    static final BreakException INSTANCE = new BreakException();
}

private static class ExitException extends RuntimeException {
    static final ExitException INSTANCE = new ExitException();
}
```

All three disable stack trace filling (`super(null, null, true, false)`) for efficiency, since they do not represent errors but simple control jumps. For example, `visitStatBreak` simply throws `BreakException.INSTANCE`, and the enclosing loop (`for`, `until`, `switch`) is responsible for catching it.

---

### Branching — `newBranch()`

One of the interpreter's most important architectural choices is the **branching** mechanism. When executing a
conditional block or a loop, locally declared variables must not leak out of the local environment, while at
the same time modifications to already existing variables must propagate. Thanks to this mechanism, the interpreter creates an isolated copy
of memory through the `copyFrom()` function, called a **branch**. When the block ends, only the modifications to pre-existing variables are merged back
into the main memory via the `mergeFrom()` function.

```java
private BagOfGrammarIntp newBranch() {
    BagOfGrammarIntp branch = new BagOfGrammarIntp(Mem.copyOf(this.mem));
    branch.creatures.putAll(this.creatures);
    branch.spells.putAll(this.spells);
    return branch;
}
```

The branch inherits a **deep copy** of the current memory (`Mem.copyOf`), as well as the table of creatures (classes) and spells (functions), which are shared by reference because they are read-only during execution.

This pattern is used, for example, in the `if` construct:

```java
@Override
public ExpValue<?> visitIfStat(BagOfGrammarParser.IfStatContext ctx) {
    BagOfGrammarIntp branch = newBranch();
    // ...
    if (visitBoolExpr(exprs.get(i)).toJavaValue()) {
        branch.visit(blocks.get(i));
        matched = true;
        break;
    }
    // ...
    mem.mergeFrom(branch.getMem());
    return null;
}
```

The executed branch works on `branch`, then `mergeFrom` synchronizes the modified variables (already existing in the main memory) without introducing into the outer context the variables declared locally in the block. This guarantees correct **scope isolation** while still propagating effects on already existing bindings.

The same happens in `visitUntilStat` and in the body of the `for`, where each iteration creates a fresh branch:

```java
BagOfGrammarIntp branch = newBranch();
try {
    branch.visit(ctx.block(0));
} catch (BreakException e) {
    mem.mergeFrom(branch.getMem());
    brokeOut = true;
    break;
}
mem.mergeFrom(branch.getMem());
```

In case of `break`, the merge still happens, in order to preserve any side effects on external variables that already occurred before the break within the loop body.

---

### Function calls — `callFunction` and `bindParams`

Spells (functions) are registered in the `spells` map during the setup phase in `registerSpells`, before the quest block is executed. When a call is encountered, `visitSpellCall` retrieves the declaration and delegates to `callFunction`:

```java
private ExpValue<?> callFunction(BagOfGrammarParser.ParamListContext params,
                                 BagOfGrammarParser.BlockContext body,
                                 List<ExpValue<?>> args) {
    mem.pushScope();
    bindParams(params, args);
    ExpValue<?> result = null;
    try {
        executeBody(body);
    } catch (ReturnException e) {
        result = e.value;
    } finally {
        mem.popScope();
    }
    return result;
}
```

The mechanism is simple: a new scope is pushed, the formal parameters are bound to the actual arguments, the body is executed, and any `ReturnException` is caught to extract its value. The `finally` guarantees the scope is popped even if the body throws an unexpected exception.

Parameter binding is delegated to `bindParams`, which iterates in parallel over the list of formal parameters and the list of computed values:

```java
private void bindParams(BagOfGrammarParser.ParamListContext params, List<ExpValue<?>> args) {
    if (params == null) return;
    List<BagOfGrammarParser.ParamContext> ps = params.param();
    for (int i = 0; i < ps.size(); i++)
        mem.declareInit(ps.get(i).ID().getText(), resolveType(ps.get(i).type()), args.get(i));
}
```

Each parameter is declared in the current scope (the one just pushed) with the type specified in the signature and the value passed as an argument. The passing is **by value**: the function receives a copy of the value, not a reference to the caller's variable.

---

### Method calls — `callMethod`

Methods are defined inside creatures (classes). `callMethod` receives the already evaluated receiver as an `ObjectValue`, together with the call context:

```java
private ExpValue<?> callMethod(ObjectValue receiver, BagOfGrammarParser.SpellCallContext callCtx) {
    String className  = receiver.getClassName();
    String methodName = callCtx.ID().getText();
    CreatureDescriptor desc = creatures.get(className);
    // ...
    mem.pushScope();
    mem.declareInit("self", new ObjectType(className), receiver);
    // ...
    bindParams(mr.paramList(), args);
    result = executeBody(mr.block());
    // ...
    mem.popScope();
    return result;
}
```

The main difference compared to `callFunction` is that the `self` variable is automatically injected into the call scope, bound to the receiver. This makes the current object accessible inside the method body using the same syntax used for any other variable. The parameters are then bound using the same `bindParams` used for free functions, making the mechanism uniform.

Creatures are registered in `registerCreatures`, which distinguishes between **fields** (type declarations) and **methods** (function declaration contexts), storing everything in the `CreatureDescriptor` associated with the class name. At `summon` time, `visitExprNew` retrieves the descriptor and initializes the fields to their default values via `defaultValue()`.

### 6.7 Error Handling

The language distinguishes two categories of errors, detected in distinct phases of execution: **static errors**, identified by the type checker before execution, and **dynamic errors**, identified by the interpreter at runtime.

---

#### Static errors — type checker

The type checker (`BagOfGrammarTS`) analyzes the AST before any execution. Since it operates on declared types and program structure — not on concrete values — it can only detect errors that are **always wrong regardless of what happens at runtime**.

Examples of static errors:

- Use of an undeclared variable
- Assignment of a value with an incompatible type
- Calling a spell with arguments of the wrong type
- Calling a non-existent method on a creature (`w.fly()` when `fly` is not defined on `Warrior`)
- Instantiating an undeclared creature (`summon Dragon()` when `Dragon` does not exist)
  If the type checker detects one or more errors, execution is **halted before it begins**:

```
[TypeCheck] line 48:8 – Unknown method 'fly' on creature Warrior
[TypeCheck] line 53:19 – Unknown creature (class): Dragon
Type error(s) found. Execution aborted.
```

This guarantees that the program is never executed in a structurally inconsistent state.

---

#### Dynamic errors — interpreter

Some errors cannot be detected statically because they depend on **concrete values** available only at runtime. These are handled by the interpreter through the `RuntimeError` class.

```java
public class RuntimeError extends RuntimeException {
    private final int line;
 
    public RuntimeError(String msg, int line) {
        super(msg);
        this.line = line;
    }
 
    // ...
    
    @Override
    public String toString() {
        if (line >= 0)
            return "[Runtime Error] line " + line + ": " + getMessage();
        else
            return "[Runtime Error] " + getMessage();
    }
}
```

When the interpreter detects an error condition, it throws a `RuntimeError` with a descriptive message and, where available, the source line number. The exception propagates up the stack to `Main`, which catches it and prints it in a readable format without producing a stack trace:

```java
try {
    BagOfGrammarIntp interpreter = new BagOfGrammarIntp();
    interpreter.visit(tree);
} catch (RuntimeError e) {
    System.err.println(e.toString());
    System.exit(1);
}
```

Detected dynamic errors include:

| Scenario | Message                                                                          |
|---|------------------------------------------------------------------------------------|
| Division by zero | `Can't divide by 0!`                                                               |
| User input not convertible to the expected type | `Expected an integer value, got: 'pippo'`                                          |
| Field access on a non-object value | `Cannot access field 'name' on a non-creature value (inside string interpolation)` |

The interpreter also handles other types of errors; however, these errors are caught earlier by the type checker.
These checks are present in the interpreter as a defensive safety net, in case the interpreter is used in the future without going through the type checker.

| Scenario | Message |
|---|---|
| Call to a non-existent method at runtime | `Unknown method 'fly' on creature Warrior` |
| Instantiation of an unknown creature at runtime | `Unknown creature: 'Dragon'` |
| Undeclared spell | `Unknown spell: 'phantom_strike'` |

For example, division by zero is intercepted in `visitExprMulDivMod`, before the division is actually performed, by checking whether the divisor is zero:

```java
if ("/".equals(op) || "%".equals(op)) {
    Object javaValue = right.toJavaValue();
    if (javaValue instanceof Number && ((Number) javaValue).doubleValue() == 0.0)
        throw new RuntimeError("Can't divide by 0!", ctx.start.getLine());
}
return applyArith(left, right, op);
```

The check uses `doubleValue() == 0.0` to uniformly cover both `Int` and `Float` operands.
 
---

#### Separation of concerns

The distinction between the two error categories reflects a precise separation of responsibilities:

- The **type checker** detects *type and structural* errors — what is wrong by construction, regardless of execution.
- The **interpreter** detects *value and behavioral* errors — what depends on data known only at runtime, such as user input or the result of a computation.
  This architecture guarantees that well-typed programs are executed safely, and that inevitably dynamic errors are still presented to the user in an understandable form.

```
// ==================================================
//  ANTLR & DRAGONS — DemoCast.bag
//  Showcase of implicit and explicit casting rules
//
//  Menu options:
//      1. Implicit widening: HP -> Int
//      2. Implicit widening: QuestName -> String
//      3. Implicit widening: Int -> Float
//      4. Explicit narrowing: Int -> HP
//      5. Explicit narrowing: String -> QuestName
//      6. Explicit narrowing: Float -> Int (truncation)
//      7. Runtime cast failure: (Int) on non-numeric input
//      8. Exit
// ==================================================

quest:
{
    narrate "========================================";
    narrate "   ANTLR & DRAGONS — Cast Showcase     ";
    narrate "========================================";
    narrate "";

    Bool running = true;

    until(running eq false){
        narrate "Select a scenario:";
        narrate "  1. Implicit widening: HP -> Int";
        narrate "  2. Implicit widening: QuestName -> String";
        narrate "  3. Implicit widening: Int -> Float";
        narrate "  4. Explicit narrowing: Int -> HP";
        narrate "  5. Explicit narrowing: String -> QuestName";
        narrate "  6. Explicit narrowing: Float -> Int (truncation)";
        narrate "  7. Runtime cast failure: (Int) on non-numeric input";
        narrate "  8. Exit";
        narrate "";

        Int choice = declare(Int, "Choose an option [1-8]: ");
        narrate "";

        switch(choice){
            case 1:
                // HP is a subtype of Int — widening is implicit
                HP hero_hp = (HP) 42;
                Int hp_as_int = hero_hp;
                narrate i"HP value:       ${hero_hp}";
                narrate i"As Int (impl.): ${hp_as_int}";
                break;
            case 2:
                // QuestName is a subtype of String — widening is implicit
                QuestName quest_name = (QuestName) "Defeat the Dragon";
                String name_as_string = quest_name;
                narrate i"QuestName value:      ${quest_name}";
                narrate i"As String (impl.):    ${name_as_string}";
                break;
            case 3:
                // Int widens to Float implicitly
                Int gold = 7;
                Float gold_ratio = gold;
                narrate i"Int value:        ${gold}";
                narrate i"As Float (impl.): ${gold_ratio}";
                break;
            case 4:
                // Int -> HP requires explicit cast (narrowing)
                Int raw_hp = 100;
                HP explicit_hp = (HP) raw_hp;
                narrate i"Int value:          ${raw_hp}";
                narrate i"As HP (explicit):   ${explicit_hp}";
                break;
            case 5:
                // String -> QuestName requires explicit cast (narrowing)
                String raw_name = "Slay the Lich King";
                QuestName explicit_quest = (QuestName) raw_name;
                narrate i"String value:             ${raw_name}";
                narrate i"As QuestName (explicit):  ${explicit_quest}";
                break;
            case 6:
                // Float -> Int requires explicit cast — decimal part is truncated
                Float pi = 3.14;
                Int truncated = (Int) pi;
                narrate i"Float value:        ${pi}";
                narrate i"As Int (explicit):  ${truncated}  <- decimal part truncated";
                break;
            case 7:
                // declare(Any) accepts any input — casting to Int fails at runtime
                // if the user types a non-numeric value (e.g. 'ciao')
                narrate "Type something that is NOT a number (e.g. 'ciao'):";
                Any raw_input = declare(Any, "> ");
                Int parsed = (Int) raw_input;
                narrate i"Parsed as Int: ${parsed}";
                break;
            case 8:
                flee;
            default:
                narrate "Invalid choice. Please select a number between 1 and 8.";
        }

        narrate "";
    }
}
```
